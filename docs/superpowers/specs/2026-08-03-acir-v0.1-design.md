## Purpose

Agentic Circuit is an agent-first architecture-modeling toolchain. A coding
agent writes a Python architecture, validates it through deterministic CLI
stages, lowers it through MLIR, generates a structured pure C++ gfsim model, and
runs that model using a versioned PTO JSON trace.

The system models computation, storage, queues, resources, buses,
interconnects, routing, scheduling, address spaces, protocols, and timing at a
high transaction level. It is not an RTL construction language.

This document is the design hub. All normative specifications share one

The Markdown specifications add cross-record and execution semantics that JSON
Schema cannot express.

When this design summary conflicts with a normative child specification, the
child specification controls its own domain.

## End-to-end flow

```text
Agent writes architecture.py
  -> frontend syntax and API validation
  -> deterministic Python AST capture and static specialization
  -> typed ACPy construction, scope inference, and verification
  -> ACPy-to-ACIR Graph-region lowering
  -> ACIR Core verification
  -> type, protocol, resource, and address validation
  -> process construction and effect verification
  -> topology freeze
  -> process continuation/state-machine lowering
  -> ACSim construction-plan validation
  -> hierarchical C++ generation
  -> C++20 concept, source-contract, and build validation
  -> gfsim runtime preflight
  -> PTO trace-driven simulation
  -> runtime and post-run validation
```

Build and run stages produce immutable, fingerprint-linked manifests and may be
run independently through the CLI.

## Architectural layers

### Python elaboration

Python provides assignment-and-call dataflow, familiar static control flow,
reusable module functions, parameterization, strong hierarchy scopes, and JIT
specialization for static architecture generation. Parameters and returns
define module interfaces; lexical capture and escape analysis define strong
scope interfaces. Python control flow that affects topology executes during
elaboration.

The frontend parses decorated Python AST into a typed, source-mapped ACPy
semantic IR before emitting ACIR. Explicit `ins()`, `outs()`, and `connect()`
calls are not required in ordinary architecture code.

Python is not the stored canonical representation and is not required by the
generated simulator.

All architecture and component parameters are static specialization inputs.
Python metaprogramming fixes topology, policies, capacities, latency, bandwidth,
time domains, address maps, and instrumentation profiles before ACIR freeze.
PTO trace data and simulator stop/output controls are run inputs, not runtime
model configuration.

### ACIR Core

ACIR is the stable frontend/compiler boundary. Its topology is static after
`ac-freeze-topology`. Runtime control uses `ac.process`, standard MLIR `scf`, and
explicit suspension points.

ACIR Core contains universal semantics rather than a closed set of architecture
components.

### ACIR Standard Library

Traditional components are registered modules with machine-readable
`ComponentSchema` definitions and reusable C++ templates.

The initial library includes compute, control, interconnect, transport, storage,
synchronization, adaptation, and workload families. Later implementations may
add components, policies, protocols, and providers without modifying ACIR Core.

### ACSim lowering

ACSim is a thin construction IR used only for C++ generation. It records
specialized types, ownership, construction, typed binding calls, inline pure
expressions, process state-machine layout, static activation adjacency, and
runtime registration. It contains no component behavior, queue algorithm,
latency calculation, arbitration, or protocol implementation.

Architecture optimization happens in ACIR before ACSim lowering.

### gfsim

Generated gfsim is fully specialized pure C++. It preserves module and
collection hierarchy and uses an Agentic Circuit-owned C++20 model library. The
library reuses the established `SimObject`, `Module`, `SimQueue`, `SimSystem`,
`Work`, and `Xfer` concepts, but Agentic Circuit's event-driven semantics are
canonical and do not promise cycle compatibility with existing Linx or
DavinciOO models.

The scheduler invokes a component only after an input epoch change, due event,
process wakeup, pending commit, or explicit internal wakeup. When no object is
active, time jumps to the next event. The v0.1 implementation is a single-thread
reference scheduler whose component contract is parallel-safe; later concurrent
schedulers must be bit-identical.

## Agent-first CLI

The public command is `agentic-circuit`, with optional alias `acirc`.

The primary workflow is:

```text
agentic-circuit schema component --json
agentic-circuit check architecture.py --json
agentic-circuit inspect graph --json
agentic-circuit build architecture.py
agentic-circuit run architecture.py --trace trace.json --output-dir run
```

The CLI provides deterministic non-interactive operation, structured diagnostic
codes, source and hierarchy locations, fix suggestions, stage control,
intermediate artifacts, component discovery, build caching, and replay manifests.

## Validation philosophy

Validation is not one final compiler pass. Each representation validates its own
contract before the next representation is created.

Required gates are:

- exact contract-epoch validation;
- Python/frontend validation;
- typed ACPy construction and scope inference validation;
- static elaboration validation;
- ACIR type and protocol validation;
- resource and address-map validation;
- topology-freeze validation;
- process and ACSim validation;
- generated C++ and model-library source-contract validation;
- trace and runtime preflight;
- runtime invariant monitoring;
- post-run conservation and completion validation.

All gates emit the same diagnostic envelope with stage, stable code, severity,
source location, hierarchy path, expected value, actual value, related objects,
and possible repairs.

## Static and dynamic boundary

Static topology includes:

- modules and instances;
- arrays and heterogeneous instance collections;
- ports, interfaces, channels, and protocols;
- queues, resources, address spaces, and address maps;
- implementation and policy selection;
- time domains;
- functional-model and validation profiles;
- stable hierarchy paths.

Dynamic behavior includes:

- trace traversal;
- transaction and packet lifetime;
- queue occupancy;
- resource reservations;
- local arbitration;
- event latency;
- process continuation;
- storage state;
- probes and statistics.

Runtime creation or rewiring of architecture topology is outside v0.1.
Runtime mutation of model parameters is also outside v0.1.

## Structured hierarchy

`ac.module` is a semantic ownership and hierarchy boundary. Each specialized
module generates a distinct C++ class or template specialization. Parent modules
own child modules, local queues, resources, processes, probes, and statistics.

Generated C++ MUST NOT use a flattened global table as its primary ownership
model. Non-owning scheduling and introspection registries are permitted.

Canonical hierarchy paths are shared by Python diagnostics, ACIR, C++ runtime,
probes, logs, statistics, and replay manifests. Human-readable paths are
separate from content and build fingerprints.

## Types, packets, and protocols

ACIR distinguishes:

- struct: logical named product value;
- packet: immutable serialized transport value;
- transaction: logical operation spanning one or more packet phases;
- tile: payload/schema concept rather than a module;
- interface: role-aware bundle of channels;
- protocol: event/state handshake and transfer contract.

Protocols model transaction events rather than RTL wires and support ready-valid,
credit, request-response, retry, cancellation, correlation, ordering, and
delivery guarantees.

## Resources and addresses

`ac.resource` exposes finite service capacity, issue width, initiation interval,
latency, reservation, release, and arbitration ownership. It allows ACIR passes
to understand compute lanes, link lanes, memory banks, and DMA channels without
forcing them into one component class.

`ac.address_space` and `ac.address_map` describe address widths, ranges,
interleave, translation, target selection, and unmapped behavior. This prevents
memory routing semantics from being hidden entirely inside opaque C++ templates.

## Standard library decisions

The initial component concepts are normalized as follows:

| Concept | v0.1 treatment |
| --- | --- |
| Tile | Payload and schema, not a component family. |
| Compute | Compute family. |
| Scheduler | Stateful control module or resource policy. |
| Link | Interconnect family. |
| Bus | Interconnect family. |
| Crossbar | Interconnect family. |
| DMA | Transport family. |
| Priority Bus | Bus plus QoS/arbitration policy, not a separate component. |
| Storage | Storage family with register file, scratchpad, cache, memory, and controller variants. |

The initial library additionally includes router, protocol adapter, address
translator, dependency tracker, synchronization, and trace-source components.

New components are added through namespaced providers and exact-epoch
`ComponentSchema` declarations. A new public schema changes the lockstep
contract epoch, although it normally does not require a new ACIR operation.

The v0.1 catalog separates `declared_unavailable` schemas from `available`
implementations. The first executable baseline requires TraceSource, finite
Queue, Scheduler, Compute, point-to-point Link, Memory/Sink, ready-valid, and
request-response. An unavailable component fails during call resolution and
never lowers to a stub.

## PTO trace boundary

Generated gfsim reads an exact-epoch PTO trace from JSON. Exactly one
`TraceSourceModel` owns each cursor, parses and validates JSON, retains a pending
decoded record under backpressure, and advances the cursor only on committed
transfer. It emits typed ACIR packets or transactions.

Compute, storage, interconnect, DMA, and scheduling components do not depend on
JSON field spelling or schema evolution.

## Selected v0.1 decisions

- Agentic Circuit is a standalone repository.
- All public contracts use one exact lockstep epoch; interface changes are hard
  breaks and Git is the only rollback mechanism.
- ACIR is independent of pyCircuit's bit-level PYC dialect.
- Python performs static elaboration; ACIR is the canonical compiler boundary.
- All model parameters are static and all generated C++ is specialized.
- Architecture topology is static after an explicit freeze pass.
- ACIR topology uses Graph-region typed SSA bindings; it has no `ac.connect`.
- Standard MLIR `scf` is allowed only in permitted executable regions.
- Cross-cycle waits use explicit suspension operations.
- `@process` suspension lowers to an enum-PC C++ state machine, not a coroutine
  or interpreter.
- Struct, packet, transaction, interface, channel, and protocol are separate
  concepts.
- Generated C++ preserves module and collection hierarchy.
- Component implementations use reusable exact-epoch C++20 templates and
  concepts owned by this repository.
- Shared-resource arbitration is owned locally by the resource owner.
- gfsim uses conservative discrete-event, cycle-equivalent execution with
  integer global ticks and causal delta barriers.
- Zero-delay propagation is restricted to pure stateless operations; stateful
  objects commit at most once per tick.
- Pure operations inline into generated C++ and do not become runtime objects.
- The runtime uses a generated static dispatch table and activation adjacency.
- Validation and instrumentation are compile-time build profiles.
- Functional computation is an optional compile-time component policy.
- Core IR defines resources and address maps but not a closed component catalog.
- Standard-library providers may add components without changing ACIR Core, but
  any new public schema changes the lockstep epoch.
- gfsim reads PTO JSON at runtime through a dedicated trace subsystem.
- Every compilation and runtime layer is independently validated.

## v0.1 acceptance summary

The first conforming implementation enables an agent to:

- discover components, interfaces, protocols, and parameters as JSON;
- write and validate a hierarchical Python architecture;
- create homogeneous arrays and heterogeneous instance collections;
- define structs, packets, transactions, and handshake protocols;
- describe finite queues, resources, address maps, and time domains;
- inspect the elaborated graph and canonical paths;
- lower structured control with suspension points;
- generate a hierarchical pure C++ gfsim binary;
- bind baseline standard-library C++ templates;
- validate and stream a PTO JSON trace;
- run deterministically with finite queues, local arbitration, and latency
  events;
- skip inactive components and jump over idle time without changing the
  reference cycle-equivalent result;
- receive structured build, runtime, deadlock, and post-run diagnostics;
- reproduce the run using immutable `run-manifest.json` as the only replay
  input; that manifest references the exact `build-manifest.json`, and results
  are written to `run-result.json`;
- distinguish completed, intentionally expected capped, incomplete, and failed
  runs.

## Deferred features

The following remain outside v0.1:

- hierarchy flattening;
- bit-level RTL lowering;
- dynamic topology mutation;
- distributed or optimistic parallel simulation;
- a production multi-thread scheduler, although the v0.1 component contract is
  parallel-safe;
- unbounded packet payloads;
- automatic formal liveness proof;
- mandatory cache-coherence protocols;
- SystemC or Verilog generation;
- binary PTO trace format;
- safe sandboxing of untrusted Python elaboration;
- dynamic component plugin loading inside generated gfsim.
- runtime model configuration or runtime component-policy switching.
